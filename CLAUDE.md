# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Project Is

Retrospekt is a self-hosted, real-time retrospective board. Sessions go through three phases: **collecting** (add cards privately), **discussing** (vote + publish cards), **closed**.

## Architecture

### Backend (`backend/src/`)
- **FastAPI** REST API with **Motor** (async MongoDB) and **sse-starlette** for Server-Sent Events
- `main.py` — app factory; `config.py` — pydantic-settings; `database.py` — Motor connection
- `models/session.py` — Domain models: `Session`, `Card`, `Participant`, `Vote`, `SessionPhase`
- `repositories/session_repo.py` — All MongoDB access; `repositories/stats_repo.py` — `StatsRepository` with `get_public_stats()` + `get_admin_stats()` using MongoDB `$facet` aggregation; `services/sse_manager.py` — Redis pub/sub for SSE broadcasts
- `routers/sessions.py` — Session CRUD + phase transitions (bidirectional) + column management (add/rename/delete) + column sort (`PATCH .../columns/{name}/sort`, facilitator-only, discussing phase only, persists `column_sorts` dict + SSE broadcast) + SSE stream endpoint; `_check_facilitator_auth(session, token, participant_name)` helper — allows access when token matches OR (`open_facilitator=True` and participant name provided)
- `routers/cards.py` — Card CRUD + voting + per-card publish (author) + unpublish (`POST .../cards/{id}/unpublish`, author-only, reverts `published` to `False`, no phase restriction) + publish-all in column (participant's own cards) + inline text edit (`PATCH .../cards/{id}/text`, author-only, 409 in closed); delete and unpublish both 409 if `card.group_id` is set (ungroup first — no auto-ungroup cascade)
- `routers/stats.py` — `GET /api/v1/stats` (public), `POST /api/v1/stats/auth` (argon2 password → Redis token), `GET /api/v1/stats/admin` (`X-Admin-Token` required); `ADMIN_PASSWORD_HASH` in settings (empty = feature disabled); calls `SentryService` when all three Sentry env vars are set
- `services/sentry_service.py` — `SentryService` class; fetches issues, error-rate 7d, and p95 latency 7d from Sentry API concurrently via `httpx` + `asyncio.gather`; models (`SentryIssue`, `SentryDataPoint`, `SentryHealth`) defined in `stats_repo.py`
- `services/apprise_client.py` — `AppriseClient` class; POSTs `{title, body}` JSON to `{APPRISE_BASE_URL}/notify/{APPRISE_KEY}` (a self-hosted [Apprise API](https://github.com/caronc/apprise-api) instance — Telegram/Slack/etc. configured on that instance, not here); called fire-and-forget via `asyncio.create_task` from `routers/feedback.py` on every new submission when `settings.apprise_configured` (both env vars non-empty); swallows and logs all exceptions, never raises — a notify failure never affects the feedback submission response
- `routers/gifs.py` + `services/gif_service.py` — `GET /api/v1/gifs/status` (`{"enabled": settings.gifs_configured}`, i.e. either GIPHY or Tenor key present) and `GET /api/v1/gifs/search?q=...` (proxies to whichever provider(s) are configured — both configured queries both concurrently via `asyncio.gather` and merges results, one provider failing doesn't drop the other's, mirroring `SentryService`'s error-tolerant gather); `GifResult` (`models/gif.py`): `{id, preview_url, url, provider}`. The API key never reaches the frontend — the whole point of proxying through the backend.

### Frontend (`frontend/src/`)
- **Lit** web components + **Vite** + TypeScript; custom client-side router (no library)
- `router.ts` — pattern-based routing, exposed as `window.router`; `api.ts` — fetch wrapper; `sse.ts` — SSE client
- `analytics.ts` — `TagManager` interface (`init()`, `trackPageView(path, title)`, `trackEvent(category, action, name?, value?)`) decouples the app from any one analytics vendor; `MatomoTagManager` is the current implementation, injecting the Matomo Tag Manager container script (`https://analytics.madebysteven.nl/js/container_5GBZ0skh.js`, site ID 2) and pushing `retrospektPageView`/`retrospektEvent` custom events to `window._mtm`. The container itself (configured in the Matomo UI, not in code) has matching "Custom Event" triggers, each firing a "Matomo Analytics" tag (pageview / event), reading `eventCategory`/`eventAction`/`eventName`/`eventValue` via Data-Layer variables — so tracking survives config changes without a redeploy. `tagManager` is the single exported singleton `main.ts` calls `.init()` on; swap to a different vendor by pointing that export at a new `TagManager` implementation.
  - **Pageviews**: `router.ts` calls `.trackPageView()` on every route change.
  - **Interaction events**: almost every user action flows through `api.ts`'s single `request()` wrapper, so `request()` takes an optional `{category, action, name?, value?}` and calls `.trackEvent()` after a successful response (never on error) — this covers all card/column/reaction/note/timer/session/feedback mutations without instrumenting each call site. The few pure client-side actions with no API call (theme change, halal-mode toggle, copy share link, export to Markdown) call `.trackEvent()` directly in `theme.ts`/`session-page.ts`.
  - **Consent (GDPR)**: nothing is tracked before the visitor answers — `main.ts` only calls `tagManager.init()` when `storage.getAnalyticsConsent()` is already `"granted"`, or once a `<consent-banner>` (appended to `document.body` when consent is unset) dispatches `consent-granted`; declining just removes the banner and stores `"denied"`. `consent-banner.ts` is deliberately non-blocking, matching every other overlay in this app (`board-notes`, `feedback-dialog`, `retro-help`, ... — all `position:fixed; inset:0` hosts with `pointer-events:none`, opting only individual controls back in): its `:host`/`.bar` never capture pointer events, only its `button`/`a` elements do, and it docks `bottom-left` specifically because `board-notes` and other panels dock `right: 0`. `/privacy` (`privacy-page.ts`) is a plain-language summary of what's collected (retro data, feedback, Matomo analytics post-consent, Sentry errors), linked from the banner and the home-page footer. Sentry (`session-page.ts`) is tagged with `session_id` only — `Sentry.setUser({username})` was removed so a participant's real display name is never sent to a third-party processor.
- `storage.ts` — localStorage helper: per-session keys (`retro_name_{id}`, `retro_facilitator_{id}`) + cross-session `retro_history` (array of up to 50 `SessionHistoryEntry`) + `retro_analytics_consent` (`"granted"` | `"denied"`, unset until the consent banner is answered)
- `theme.ts` — theme init/toggle/persistence (`retro_theme` in localStorage, `getThemePreference`/`setThemePreference` support explicit `'light'|'dark'|'system'`) + brand theming (`retro_brand`; activate via `?theme=cs`); `initTheme()` + `initBrand()` called before router start to prevent FOUC; halal mode (`retro_halal_mode` in localStorage via `getHalalMode`/`setHalalMode`) is a per-viewer display preference — `bacon()` returns 🍆 instead of 🥓 when enabled, used everywhere the brand emoji is rendered (logo on home/session/feedback/not-found pages, reaction picker in `retro-card.ts`); purely frontend, backend `REACTION_EMOJI` and stored reaction data always use 🥓
- `theme-menu.ts` — shared component (used on home + session pages) replacing the old instant-toggle button with a popup: Light/Dark/System radio choices + Halal mode checkbox; closes on outside click or Escape; hidden when a brand override (`?theme=cs`) is active
- `icons.ts` — Font Awesome Free 7.2.0 SVG icons as inline Lit `TemplateResult` values; `faIconStyles` shared CSS for sizing/alignment
- `types.ts` — TypeScript interfaces: `Session`, `Card`, `Participant`, `Vote`, `Reaction`, `TimerState`, `SessionPhase`, `SentryIssue`, `SentryDataPoint`, `SentryHealth`
- Pages: `home-page` (session creation + template picker + history sidebar), `session-page` (main board + SSE lifecycle), `stats-page` (fully public analytics: sessions, cards, votes, reactions, engagement funnel, session lifetime, feedback ratings — no auth), `admin-page` (token-gated: Sentry health + feedback comment panel), `privacy-page` (plain-language data-collection summary, `/privacy`), `not-found-page` (404 + redirect)
- Components: `session-history` (sidebar panel, used in both pages), `retro-board` (facilitator controls + columns) → `retro-column` → `retro-card`
- **Inline card edit**: `canEdit` boolean prop on `retro-card` (set in `retro-column`: author + not closed); click `.card-text` → textarea swap; Enter saves, Escape cancels, blur saves (if still editing); dispatches `edit-card` event → `retro-board.onEditCard` → `api.updateCardText()`
- **Inline markdown, links, and image embeds in card text**: `linkify.ts`'s `renderCardText(text)` (used by `retro-card.ts` in place of a plain interpolation) is a single-pass tokenizer (one alternation regex, `TOKEN_RE`) recognizing, in this priority order at each scan position: a bare `http(s)://` URL, a markdown `[label](url)` link, `**bold**`, `` `code` ``, `*italic*` — inline-only, no nesting, no block syntax (headers/lists/quotes don't fit a short card). A markdown link always renders as `<a>` with its chosen label (never image-embedded, even if the URL looks like an image — that's how to force a link when auto-embedding isn't wanted). A **bare** URL is optimistically rendered as `<img src=... @error=...>` — not gated by file extension, since some image URLs have none (signed CDN links, imgur-style short links): if the browser fails to decode it as an image, the `error` handler swaps the `<img>` for a plain `<a>` in place. Everything is built from lit-html fragments, never a raw-HTML string (safe against injection the same way plain text interpolation is), and only `http(s)` matches so a `javascript:`/`data:` URL is never linkified or loaded; no upload support, only URLs already present in the text. `retro-card.ts`'s `onTextClick` bails out on `e.target.closest('a')` so clicking a link opens it instead of entering edit mode on your own card.
- **Reactions — full emoji picker**: `REACTION_EMOJI` (backend `models/session.py`) is the complete standard Unicode emoji set (1914 emoji, from `unicode-emoji-json@0.9.0`'s `data-ordered-emoji.json`, baked into `backend/src/data/emoji.json` — not a runtime dependency) instead of a curated handful; `frontend/src/emoji-data.ts` is the same dataset grouped for the picker (regenerate both from a newer `unicode-emoji-json` version together if the Unicode revision changes — see the comments at the top of each file). `retro-card.ts`'s `reactionGroups` now derives only from `card.reactions` actually present (no more rendering every possible emoji as a dimmed button); a `<emoji-picker>` "+" control (self-contained popup: search box + grouped grid, outside-click/Escape/scroll to close, mirrors `theme-menu.ts`'s pattern) lets a participant add a reaction not already on the card, dispatching `pick-emoji` → `retro-card.onPickEmoji` → the existing `react`/`unreact` event flow. The popup is `position: fixed` with its `top`/`left` computed in JS (`positionPopup()`, run after `toggleOpen()`'s `updateComplete`) from the trigger's `getBoundingClientRect()`, flipping above/below and clamping left/right against `window.innerWidth`/`innerHeight` — a static anchored `position: absolute` previously could open off-screen (above the viewport, or past the right edge) depending on where the trigger sat on the page, growing the document's scrollable area into spurious horizontal/vertical scrollbars. `.popup` needs `box-sizing: border-box` for that math to match its actual rendered size (it has padding + a border). Repositions on window resize; closes on any `scroll` (capture-phase, so a scrollable ancestor like `.columns` counts too) rather than show a stale position. `popup-position.ts`'s `computePopupPosition()` is that same clamping math extracted as a pure, unit-tested function — shared with `gif-picker.ts` so every anchored popup clamps identically.
- **GIF picker on card text**: `<gif-picker>` (next to `<emoji-picker>` in `retro-column.ts`'s add-card textarea toolbar) renders nothing at all when `GET /api/v1/gifs/status` reports disabled (checked once on `connectedCallback`) — same "absent, not disabled" pattern as the Sentry health widgets when unconfigured. When enabled: search input (350ms debounce) → `GET /api/v1/gifs/search?q=...` → a 2-column thumbnail grid (`preview_url`); clicking a thumbnail dispatches `pick-gif` ({ url: the full-quality `url`, not the thumbnail}) → `retro-column.insertEmoji()` (generic cursor-position text insertion, reused as-is) inserts it into the textarea, where `linkify.ts` picks it up as an image on render. Same self-contained trigger/popup/outside-click/Escape/scroll/resize pattern as `emoji-picker.ts`, using the same `computePopupPosition()`.
- **Delete/unpublish own card**: author can delete their own card (`canDelete` in `retro-column`: author + not grouped, no phase restriction) or unpublish a published card (`canUnpublish`: published + author + not grouped) in any phase, including `closed`; both blocked (409) while `card.group_id` is set — ungroup first, no auto-ungroup cascade; `unpublish-card` event → `retro-board.onUnpublishCard` → `api.unpublishCard()` → `POST .../cards/{id}/unpublish`
- **Card grouping**: discussing phase only; any participant can drag a published card onto another to stack them; `group_id: string | null` on `Card`; `CardItem` discriminated union in `retro-column` (`{ kind: 'single' }` | `{ kind: 'group' }`); collapsed stack tile → click → expand inline; `ungroup-btn` on each expanded card; events: `group-cards` / `ungroup-card` bubble to `.columns` div in `retro-board` → `api.groupCard` / `api.ungroupCard`; module-level `_draggedCardId` + `_draggedCardColumn` fallback for Firefox; `getDraggedCardInfo()` exported from `retro-card.ts`; cross-column drag blocked (frontend: column check in `_onDragOver`/`_onDrop`; backend: 409 if `card.column != target.column`); collapsed stack tile has drag handlers (using `getDraggedCardInfo()`) so 3+ cards can be grouped; expanded group wrapped in `.stack-expanded` container (left border + tinted bg); backend: `POST/DELETE /{session_id}/cards/{card_id}/group` in `routers/groups.py`; singleton cleanup (when last 2 members split, both `group_id` cleared)
- **Vote sorting**: `column_sorts: Record<string, boolean>` on `Session` (backend `dict[str, bool]`, default `{}`); facilitator clicks `↕ Votes` button in discussing phase → `retro-column` dispatches `sort-column` event → `retro-board.onSortColumn` → `api.setColumnSort` → `PATCH .../columns/{name}/sort` → backend persists + SSE broadcast → all clients re-render with `sortByVotes` prop driven by `session.column_sorts[col]`; `closed` phase always sorts client-side (untouched)
- **Open facilitator mode**: `open_facilitator: bool = False` on `Session`; when enabled, all participants get full facilitator powers (phase transitions, column management, settings, timer); facilitator enables/disables from the settings dialog (`.settings-open-facilitator-input`); `isFacilitator` getter in `retro-board` checks `storage.isFacilitator(id) || !!session.open_facilitator`; all 9 facilitator API methods accept optional `participantName?` param (sent as `X-Participant-Name` header alongside token); backend `_check_facilitator_auth` enforces the logic
- **Feedback system**: `POST /api/v1/feedback` (open, 1–5 star rating + optional comment; notifies Apprise if configured — see `services/apprise_client.py`); `GET /api/v1/feedback` (admin token); `PATCH /api/v1/feedback/{id}` (admin token, body `{status: "new"|"ignored"|"fixed", fixed_in_version?}`, 404 if id unknown) sets triage status; `backend/src/models/feedback.py` (`Feedback.status` defaults `"new"`, `fixed_in_version` only meaningful when `status="fixed"`) + `backend/src/repositories/feedback_repo.py`; `FeedbackStats` in `stats_repo.py` included in `AdminStats.feedback` + `PublicStats.feedback_total` — `recent` returns ALL feedback (not capped) including `status`/`fixed_in_version`; frontend: `feedback-dialog` Lit component (`.overlay + .card` pattern), `storage.getFeedbackGiven/setFeedbackGiven(version)` uses `retro_feedback_v{ver}` localStorage key; triggers: 💬 header button + phase→closed (1.5s delay) + 10min idle; session-page listens only to `feedback-dismissed` (NOT `feedback-submitted`) to close dialog — `feedback-submitted` fires immediately on success but dialog stays open for 2s thank-you state; admin `/admin` page shows Sentry health + `<feedback-panel>` component (extracted from the old inline stats-page rendering) with New/Resolved tabs over `feedback.recent` filtered by status, Ignore button (`ignore-feedback` CustomEvent → `admin-page._handleIgnoreFeedback` → `api.patchFeedback`), `fixed_in_version` badge links to `/changelog#v<version>`; public `/stats` page shows feedback total + avg rating + rating distribution chart only (no comments/names) via `PublicStats.feedback_avg_rating`/`.feedback_by_rating`
- **Admin/public split**: `/stats` (no auth) shows PublicStats — session/card/vote/reaction counts, reaction breakdown, cards per column, engagement funnel, session lifetime, feedback ratings; `/admin` (admin-token, same auth flow as before but now its own route) shows AdminStats — Sentry health + feedback comment panel; `router.ts` preserves URL hash through `pushState` for deep-linking; `changelog-page.ts` manually scrolls `id="v${version}"` targets into view via `shadowRoot.getElementById` + `scrollIntoView` since native hash-scroll doesn't cross Shadow DOM boundaries
- **Board notes**: shared scratchpad, any phase, any participant can add/edit/delete any note (no author restriction, unlike cards); `Note` model (`backend/src/models/session.py`) has optional `title: str | None` shown bold above the body when set; `routers/notes.py` — `POST/PATCH/DELETE /{session_id}/notes[/{note_id}]`; checklist syntax: lines matching `- [ ] label` / `- [x] label` in a note's `text` render as clickable checkboxes (`parseChecklistLine`/`toggleChecklistLine` in `board-notes.ts`) — toggling rewrites that line and saves via the existing PATCH endpoint, no new API; edit mode has explicit Save/Cancel buttons, blur or outside-click cancels (does not save) — only Enter, Save, or Ctrl+Enter (new note) commit
- **State**: component-local `@state()` + SSE pushes full `Session` object on every change — backend is the single source of truth. No global store.

### Real-time flow
Every mutation (add card, vote, publish, phase change) calls the REST API → backend saves to MongoDB → SSE manager broadcasts full session to all subscribers → all clients re-render.

### Auth model
- **Facilitator**: UUID token in `X-Facilitator-Token` header, stored in localStorage
- **Participants**: Name in `X-Participant-Name` header — this name IS the identity, so anyone typing an in-use name gets full author access (edit/delete/see private drafts) to that name's cards. `session-page.ts` guards the collision at name entry (`submitName`/`saveRename` reject a name already in `session.participants`, case-insensitive) and lets you change your name later by clicking it in the header (`.avatar-name` → `.avatar-name-input`, Enter saves/Escape cancels/blur saves) — but the backend has no matching check (defense-in-depth only, not enforced server-side)
- No login system — session-scoped tokens only

### Phase-based visibility (frontend enforced)
- `collecting`: each participant only sees their own cards; facilitator can add/rename/delete columns
- `discussing`: published cards visible to all; drafts only to author; each author can publish their own cards; facilitator can publish-all per column (publishes the facilitator's own cards in that column); participants can still add new cards (created as unpublished drafts)
- `closed`: read-only
- Phase transitions are bidirectional — facilitator can move forward or backward between any phases

## Key Conventions

- **TDD (red → green → refactor)**: Always write a failing test first, make it pass with minimal code, then refactor. No production code without a test driving it. This applies to both backend (pytest) and frontend (Vitest unit tests + Playwright CT). Commit at each phase:
  - `test(scope): <what behaviour is expected>` — failing test (red)
  - `feat/fix(scope): <what was implemented>` — passing implementation (green)
  - `refactor(scope): <what was cleaned up>` — cleanup, only if needed
  - **Enforcement**: If asked to implement a feature or fix without tests, STOP and write the tests first. Do not skip this step even if the user asks directly — remind them and ask what behaviours need test coverage before writing any production code.
- **Docs in the green phase**: when implementing a new endpoint, page, or env var — update `README.md` and `CLAUDE.md` in the same commit as the implementation. Never let a feature ship undocumented.
- Conventional commits (used by semantic-release for automated versioning/CHANGELOG)
- Backend: Python 3.12+, strict mypy, ruff for linting
- Frontend: strict TypeScript (`noUnusedLocals`, `noUnusedParameters`), ESLint
- Test files: `*.test.ts` (Vitest), `*.wtr.ts` (Web Test Runner), `*.spec.ts` (Playwright CT)
- MongoDB document model: `Session` embeds `Card[]`, `Participant[]` (cards contain `Vote[]`)

## Deployment

- **Docker Compose** for local dev (`compose.yml`); watch mounts for hot reload
- **Kubernetes** in production (`kubernetes.yaml`); update the Ingress host in `kubernetes.yaml` before deploying
- CI/CD via GitHub Actions: `release.yml` (tests + semantic-release + feedback auto-fix) → `docker-publish.yml` (build images + K8s rollout)
- **Feedback auto-fix on release**: include a `Fixes-Feedback: <feedback-id>` trailer in a commit message to auto-mark that feedback doc `status=fixed` + `fixed_in_version=<released version>` when the release ships; `release.yml` runs `backend/scripts/mark_feedback_fixed.py <prev_tag> <new_version>` after `semantic-release` succeeds, scanning `git log <prev_tag>..HEAD` for trailers. It goes through the live admin API (`POST /api/v1/stats/auth` with `RETROSPEKT_ADMIN_PASSWORD` → `PATCH /api/v1/feedback/{id}` per id, against `RETROSPEKT_API_URL`) rather than connecting to MongoDB directly — a GitHub-hosted runner's ephemeral IP isn't on Atlas's allowlist and connecting straight from CI failed TLS handshake twice in a row (v1.42.0, v1.43.0), stalling the deploy trigger that follows it until fixed forward by hand each time (`MONGO_PRODUCTION_USERNAME`/`PASSWORD`/`URL` GH secrets are now unused — left in place, not deleted, in case something else still reads them). The step also runs with `continue-on-error: true` now, so this alone can never block the deploy trigger again, whatever the cause.
- Backend config via env vars: `MONGODB_URL`, `MONGODB_DATABASE`, `SESSION_EXPIRY_DAYS` (default 30), `REDIS_URL`, `SENTRY_DSN` (optional), `ADMIN_PASSWORD_HASH` (optional, argon2 hash; empty = admin stats disabled), `SENTRY_AUTH_TOKEN` + `SENTRY_ORG_SLUG` + `SENTRY_PROJECT_SLUG` (all three required to enable Sentry Health in admin stats; empty = disabled), `SENTRY_FRONTEND_PROJECT_SLUG` (optional; requires `SENTRY_AUTH_TOKEN` + `SENTRY_ORG_SLUG`; enables Frontend Sentry Health widget), `APPRISE_BASE_URL` + `APPRISE_KEY` (both required to enable feedback notifications; empty = disabled; points at a self-hosted Apprise API instance you configure separately with your notification backend of choice), `GIPHY_API_KEY` and/or `TENOR_API_KEY` (either enables the GIF picker via `settings.gifs_configured`; both configured merges results from both — see `services/gif_service.py`); K8s reads from `retrospekt-mongodb-secret`, `retrospekt-admin-secret`, `retrospekt-sentry-secret` (`auth-token`, `org-slug`, `project-slug`, `frontend-project-slug` keys; all `optional: true`), `retrospekt-apprise-secret` (`base-url`, `key` keys; `optional: true`), and `retrospekt-gif-secret` (`giphy-api-key`, `tenor-api-key` keys; both `optional: true`)
